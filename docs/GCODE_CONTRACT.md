# Picasso legacy G-code contract

Status: implemented in Phase 3 by `backend/app/drawing/gcode.py`, derived from the two bundled `Walldraw.ino` files. Phase 5 canonical firmware enforces a strict superset (`picasso-fw-v1`, below). Installed machine firmware remains unknown until commissioning.

## Actual interpreter behavior

Both reference sketches call `nc(String)` on each LF-terminated line in `drawfile()`. `nc()` uppercases the entire line and finds the first `X`, `Y`, and `Z` anywhere in it. It does not dispatch on G or M command numbers. A line containing X and Y moves using their parsed numeric values, regardless of its opcode. Z is processed first: positive raises the pen, zero or negative lowers it. Motion does not itself choose the pen state. See `Drawbot_C/02 arduino code/Walldraw/Walldraw.ino:310` and the firmware audit for complete source references.

There is no supported modal axis handling, unit conversion, relative motion, feed-rate control, arc dispatch, program-end handling, comment removal, serial receiver, or acknowledgement protocol. Arc helper functions in the source do not establish G2/G3 support. A G0 with X/Y does not automatically lift the pen. `G90`/`G21` are ignored rather than meaningfully supported.

For compatibility, define a **strict subset generated by Picasso**, rather than calling the existing parser a complete G-code implementation.

## Allowed generated lines

Use uppercase ASCII, ordinary fixed-point decimal numbers, single spaces, and LF line endings, with a final LF. Proposed wire/file grammar:

```text
pen-up      := G0 Z5
travel      := G0 X<decimal> Y<decimal> Z5
draw        := G1 X<decimal> Y<decimal> Z0
```

Every XY line contains **both X and Y, with X before Y and Z last**. Use three decimal places for XY initially; normalize negative zero. No scientific notation, NaN, Infinity, trailing fields, comments, line numbers, checksums, Unicode, or blank command lines. Z is a pen state, not a physical Z-axis height: 5 is positive/up and 0 is down.

Choose a maximum payload of 63 ASCII bytes per line, excluding LF, for the application contract. This is a forward-looking bounded-buffer limit; the old firmware does not enforce its declared `MAX_BUF=64` and instead grows `String`. The hardened firmware must allocate room for both payload terminator and handling any optional CR, or reject CR consistently.

Do not emit F, G2/G3, I/J/R, G20/G21, G90/G91, G28, G92, M3/M5, M2/M30, or dwell commands. Reject such raw inputs at the strict exporter boundary, or parse/normalize them through a separate declared import dialect first. Do not simply strip unknown commands and execute the remaining coordinates.

## Stroke sequence

1. Record an expected starting XY in the prepared job, and initialize validation/preview from it. Legacy SD jobs require the operator's origin procedure to establish physical and firmware `(0,0)` before each execution; file contents cannot verify that precondition. Begin with `G0 Z5`.
2. Travel to the first point of a stroke with explicit `Z5`.
3. Emit the first drawable endpoint with `G1 ... Z0`; the old parser lowers and settles the pen before moving from the stroke's starting point.
4. Emit each further endpoint with explicit `Z0`. For a closed path, explicitly include the final point equal to the start if needed.
5. Emit `G0 Z5` before travelling to another stroke. After the last stroke, emit `G0 Z5` and then `G0 X0.000 Y0.000 Z5\n`. The file always ends with the pen raised back at its `(0,0)` start.

`(0,0)` is the centre of the selected page. Every drawing's bounds are centred there, apart from any explicit offset the operator sets. Every job starts there with the pen up, and the final pen-up travel brings it back, so a completed job leaves the carriage ready for the next one. The parser rejects a file that does not end pen up at its declared start, and the return travel is validated like any other segment. Do not release the motors at job end unless the verified hardware profile and operator workflow explicitly support it. A one-point stroke has no drawable segment and should be rejected or removed under a documented policy.

The legacy `pen_up()` has no settling delay. Consecutive pen-up and travel lines do not guarantee that the pen has physically cleared the paper. Export compatibility alone cannot fix that; pen-up bench checks or the Phase 5 timing fix remain necessary before marking physical operation verified.

## Illustrative square

This demonstrates encoding only. It is not a ready-to-run file: actual origin, calibration, workspace and pen behavior must be verified first.

```gcode
G0 Z5
G0 X-10.000 Y-10.000 Z5
G1 X10.000 Y-10.000 Z0
G1 X10.000 Y10.000 Z0
G1 X-10.000 Y10.000 Z0
G1 X-10.000 Y-10.000 Z0
G0 Z5
G0 X0.000 Y0.000 Z5
```

The G0/G1 words make exported files readable to normal tooling; explicit coordinates and Z state provide compatibility with the legacy parser. Future firmware should enforce actual opcode semantics for exactly this documented subset rather than continue accepting arbitrary coordinate-bearing lines.

## Geometry and export checks

Before preparing a physical job:

- Require a selected, verified machine profile; never choose between the 350 and 400 mm references automatically.
- Convert requested paper/drawing dimensions to millimetres and apply centering/placement transforms explicitly. An 11×14-inch page is 279.4×355.6 mm; its sample coordinates do not establish that it fits this machine.
- Flatten every curve to bounded-error XY polylines. Keep chord tolerance and point count recorded in the job.
- Validate finite values, explicit dimensions, stroke sizes, total points/bytes, travel order, approved region, and rope geometry. Validate segments as well as endpoints, including pen-up travel.
- Include the first travel from the declared starting XY. A preceding job can leave the carriage elsewhere even when the origin reference remains valid. USB start must verify that position and current session/reference; legacy SD requires the documented operator start procedure. A mismatch requires a new preparation or an explicitly validated preposition route.
- Round to output precision, then validate again. Segment bounds can change near margins after rounding.
- Parse the exact final bytes back into ordered pen/travel segments, initialized at the declared start. Compare them against the transformed intended geometry within the recorded rounding tolerance.
- Freeze the bytes/hash/profile revision. Preview and transfer use that artifact without independent regeneration.

There is no approved physical workspace in Phase 1. `±175` or `±200` X limits and `±250` Y macros are reference values, not enforced limits or validated sheet sizes. Keep simulation separate from authorization to move.

## Imported files and sample reuse

Phase 4 accepts this strict subset and a separately declared absolute-mm linear dialect. The latter resolves modal axes, strips balanced comments, maps Z≤0 to pen down and Z>0 to pen up, accepts G17/G21/G90 and standalone M2/M30, and rejects arcs, relative/inch coordinates, offsets and unknown semantics. Feed is explicitly ignored because legacy firmware cannot honor it. Source pen-up detours are regenerated between strokes; source motions are not copied verbatim. The exact known vendor branding banner is recognized only before commands. Imports are always centred on the page centre `(0,0)`. Their original bounds and chosen fit are retained. See [STORAGE_AND_COMMISSIONING.md](STORAGE_AND_COMMISSIONING.md).

The current mandala file includes standard setup/end commands and positive paper coordinates. Other samples contain exporter headers/comments and varying Z patterns. Preserve originals, import into canonical paths, transform and validate, then regenerate restricted output. Copying a sample as `main.nc` without that process is not a compatibility strategy.

The Phase 1 audit tool reports explicit coordinate tokens, ignored-comment statistics, and potentially troublesome line patterns. It deliberately does **not** simulate modal G-code, validate machine bounds, or certify these files for execution.

## Canonical firmware enforcement (Phase 5)

`firmware/WallDrawingMachine/` parses `picasso-fw-v1`. That dialect accepts every line this contract emits, plus `G00`/`G01`, lowercase letters, any word order, optional spacing between words, `;` and balanced non-nested `( )` comments, CRLF line endings and an unterminated final line. Each command needs exactly one G0/G1 and an explicit Z. X and Y must appear together. A G0 must raise (Z>0) and a G1 must lower (Z≤0). Anything else fails: unknown words or opcodes, duplicate words, malformed or exponent numbers, more than 4 integer or 5 fraction digits, NUL, non-ASCII bytes, a bare CR, or more than 63 payload bytes.

The firmware reads the entire file and validates every segment, starting at `(0,0)`, against the compiled workspace, the anchor branch and the rope limits **before any motion**. It then shows the move count and the file's CRC-32 (`PreparedJob.gcode_crc32`). Its limits allow 0.01 mm of float tolerance, so it never rejects a job the host approved. Host tests compare the firmware parser line by line with every generator's export and compare its geometry verdicts with `validate_physical_path`. The raw vendor samples are rejected (header comment over 63 bytes, modal pen state), which is the intended outcome. See [firmware/README.md](../firmware/README.md).

## Future serial framing

Implemented in Phase 6: [SERIAL_PROTOCOL.md](SERIAL_PROTOCOL.md). Do not send legacy file bytes to the USB port and expect motion. Protocol v1 wraps this restricted command language in a separately versioned framing protocol with a handshake, session/sequence IDs, bounded sizes, acknowledgements and control messages. That protocol must retain the same stroke geometry and pen mapping. Device capability negotiation determines whether streaming, SD upload, speed control, or pause is supported.
